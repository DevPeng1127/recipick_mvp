# Recipick MVP

AI 기반 냉장고 식재료 관리 및 메뉴·레시피 추천 서비스

개발 흐름은 [개발 이력](docs/development-history.md), 기능별 결정·검증은 [기능 개발 기록](docs/feature-roadmap.md), 최신 인계 상태는 [코드 점검·인계 기록](docs/code-audit-and-repair-log.md)을 참고하세요. 개발 이력 문서에는 커밋 조회와 CSV 내보내기 방법도 있습니다.

## Tech Stack

- **Backend**: Python 3.10+, FastAPI, SQLAlchemy (async), Alembic
- **Frontend**: React 18, TypeScript, Vite, Tailwind CSS, Zustand, React Router
- **Database**: PostgreSQL 16+ (Native)
- **AI**: LangGraph + Gemini 3.5 Flash-Lite
- **Auth**: OAuth 2.0 (Kakao/Google) + JWT

## Prerequisites

- Python 3.10+
- Node.js 20.19 이상(20.x), 22.13 이상(22.x), 또는 24 이상 — 린트 도구의 실행 조건
- npm 11.19.1 이상(11.x) — 검증 버전은 11.19.1이며 `frontend/package.json`에 기록
- PostgreSQL 16+

## Setup

### 1. Database

```bash
# PostgreSQL에 recipick DB 생성
createdb recipick
# 테스트용 DB
createdb recipick_test
```

### 2. Backend

```bash
cd backend
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS/Linux
source .venv/bin/activate

pip install -e ".[dev]"

# 환경 변수 설정
cp .env.example .env
# .env 파일에서 DB URL, API 키 등 설정

# JWT 서명 키 생성 후 출력값을 .env의 JWT_SECRET_KEY에 설정
python -c "import secrets; print(secrets.token_urlsafe(32))"

# DB 마이그레이션
alembic upgrade head

# 개발 서버 실행
uvicorn app.main:app --reload
```

`JWT_SECRET_KEY`는 개발·운영 모두 필수입니다. 누락, 빈 값, 공개된 기본값, 32바이트 미만 값, 앞뒤 공백이 있는 값은 서버 시작 시 거부됩니다. 키는 한 번 생성해 환경 설정에 보관하며 서버 재시작마다 새로 만들지 않습니다. 키를 교체하면 기존 로그인 토큰과 진행 중인 OAuth 인증 상태가 무효화되므로 서버 재시작 후 다시 로그인해야 합니다.

#### Gemini 무료 개발 설정

`backend/.env`에 `GEMINI_API_KEY`와 `GEMINI_MODEL=gemini-3.5-flash-lite`를 설정합니다. 기존 `.env`가 있다면 모델 항목도 직접 바꿔야 합니다. 코드의 기본값이나 `.env.example`만 변경해도 기존 `.env`를 덮어쓰지는 않습니다. 실행 중인 백엔드는 설정 변경 후 재시작합니다.

- Google AI Studio의 **Projects → Billing Tier**에서 해당 API 키의 프로젝트가 **Free**인지 확인합니다. 무료 개발에는 이 프로젝트의 키를 사용하며 유료 등급으로 업그레이드할 필요가 없습니다. 모델 이름을 바꿔도 프로젝트의 결제 등급은 바뀌지 않습니다. [과금 안내](https://ai.google.dev/gemini-api/docs/billing)
- 2026년 10월 19일 확인 기준, 이 모델의 일반 텍스트 입력·출력은 무료 등급에서 무료입니다. 무료 등급의 입력·응답은 Google 제품 개선에 사용될 수 있으므로 개발 검증에는 가상 식재료·설정을 사용합니다. [가격과 데이터 사용 안내](https://ai.google.dev/gemini-api/docs/pricing)
- 분당 요청·토큰 수와 일일 요청 한도는 AI Studio에 표시되는 실제 프로젝트 한도를 확인합니다. 한도 초과 시 요청이 제한됩니다. [사용량 제한](https://ai.google.dev/gemini-api/docs/rate-limits)

호출은 기존 REST `generateContent`를 사용합니다. Gemini 3 권장 temperature `1.0`, 모델 기본 추론 수준(3.5 Flash-Lite는 `minimal`), 기존 `maxOutputTokens=2048`과 HTTP 단계별 타임아웃 30초를 적용합니다. HTTP 요청 전체에는 추가로 60초 제한을 둡니다. 완결된 응답의 텍스트 조각만 합쳐 레시피로 반환하며, 답변 없이 차단되거나 출력 한도로 잘린 응답은 성공으로 처리하지 않습니다. 자동 재시도나 다른 모델로의 전환은 하지 않습니다.

API 키는 [Google의 인증 방식](https://ai.google.dev/api#authentication)에 따라 `x-goog-api-key` 헤더로 전달합니다. 요청 URL과 본문에는 넣지 않으며, 설정 객체의 문자열·JSON 출력에서는 마스킹합니다. Gemini의 HTTP·연결·시간 초과·JSON 해석 오류는 내부 오류로 변환해 원문이 서버에 다시 출력되지 않도록 처리합니다. 앱 오류 로그에는 요청 방식·라우트 패턴·오류 종류·공급자 상태 코드·코드 위치만 남기고, 응답 본문·인증 헤더·예외 원문·지역 변수는 기록하지 않습니다. 레시피 추천의 공급자 HTTP·연결·시간 초과 또는 구조 검증 실패는 HTTP 502로 안내하며, 사용량 초과는 아래의 HTTP 429 안내를 유지합니다.

#### AI 사용량 제한 — 메뉴 추천·영수증·음성 인식 합산

| 대상 | 동시 요청 | 최근 60초 | 하루 | 하루 초기화 기준 |
| --- | --- | --- | --- | --- |
| 로그인 계정별 | 1건 | 3회 | 20회 | 한국 시간 자정 |
| 앱 전체 | 계정별 제한 적용 | 12회 | 400회 | 미국 태평양 시간 자정, 서머타임 반영 |

- Gemini 호출 직전에 횟수를 DB에 기록합니다. 성공·공급자 오류·시간 초과는 집계하며, 권한 거부·식재료 없음·앱의 한도 초과처럼 AI 호출 전에 끝난 요청은 집계하지 않습니다. 서버 재시작 후에도 횟수는 유지됩니다.
- 제한 시 HTTP 429와 이유를 반환하고, 확정할 수 있는 재시도 시각을 화면에 한국 시간으로 표시합니다. 진행 중인 요청이나 Google이 재시도 시간을 제공하지 않은 경우에는 정확한 시각을 임의로 안내하지 않습니다.
- 기존 개발 환경에도 `cd backend` 후 `alembic upgrade head`를 실행해 `recipe_usage_attempts` 테이블을 생성해야 합니다. 적용 후 실행 중인 백엔드를 재시작하거나 개발 서버의 자동 재로딩을 확인합니다. DB에 기록할 수 없으면 AI 호출을 진행하지 않습니다.
- 사용량 기록은 성공·실패 요청의 트랜잭션과 별도로 저장합니다. 짧은 PostgreSQL 잠금으로 여러 프로세스의 한도 확인·기록을 직렬화하고, AI 응답을 기다리는 동안에는 이 잠금을 유지하지 않습니다. 비정상 종료로 남은 진행 상태는 90초 뒤 풀립니다. 2일보다 오래된 사용량 기록은 다음 허용 요청에서 정리합니다.
- 제한값은 `backend/app/services/recipe_usage.py`에 있습니다. 같은 DB를 사용하는 앱 프로세스가 집계 대상이며, 같은 Google 프로젝트를 사용하는 다른 앱의 호출량이나 별도의 입력 토큰 한도(TPM)를 추적하지는 않습니다. Google에서 한도 초과가 발생하면 별도 안내를 표시합니다.
- 영수증·음성 인식도 같은 사용량 기록과 동시 요청 한도를 사용합니다. 기능마다 별도 20회/400회를 제공하지 않습니다. 손상·크기 초과 이미지나 유효하지 않은 녹음 등 AI 호출 전에 거절한 입력은 집계하지 않으며, 후보 확인 후 재고를 저장하는 동작은 AI 횟수를 사용하지 않습니다.

### 3. Frontend

```bash
cd frontend
npm ci
npm run dev
```

`npm ci`는 커밋된 `package-lock.json`의 버전대로 설치합니다. Node 22.19.0 / npm 11.19.1에서 검증했습니다. 기존 npm 10.9.3에서는 Vitest 의존성 설치 중 `edgesOut` 오류가 발생하여 npm을 업데이트했습니다. 다른 PC에서도 먼저 `node --version`과 `npm --version`을 확인합니다. `packageManager` 항목만으로 시스템 npm이 자동 업데이트되지는 않습니다.

Windows PowerShell에서 호스트·포트 옵션을 추가할 때는 `npm.cmd run dev -- --host 127.0.0.1 --port 5175 --strictPort`를 사용합니다. 이 환경에서는 `npm`의 PowerShell 실행 파일이 옵션을 가로채는 현상이 확인되었습니다.

설치 스크립트는 `package.json`의 `allowScripts`에서 검토한 `esbuild@0.25.12`, `msw@2.12.10`만 허용합니다. 패키지 업데이트 후 새 스크립트 승인이 필요하면 `npm install-scripts ls`로 확인하고 검토한 항목만 승인합니다. [npm 설치 스크립트 안내](https://docs.npmjs.com/cli/v11/commands/npm-install-scripts/)

#### 의존성 보안 점검

2026년 10월 19일 업데이트 후 `npm audit` 결과는 24건에서 **7건(High 5, Moderate 2)**으로 줄었고, `npm audit --omit=dev`는 **0건**입니다. 전체 감사는 남은 항목 때문에 종료 코드 1을 반환합니다. Tailwind 3을 유지하기로 한 결정에 따라 `braces`와 `postcss-selector-parser`의 문제가 개발 의존성 7개에 걸쳐 남아 있습니다. 이는 전체 프로젝트의 취약점이 없다는 의미는 아닙니다. 원인·영향 조건·후속 검토 사항은 [항목 10 기록](docs/code-audit-and-repair-log.md#항목-10-수정-기록)을 참고합니다.

## 잘못 등록한 식재료 삭제

식재료 메뉴의 **수정/삭제 → 식재료 삭제 → 삭제하기**에서 중복 등록·입력 실수 항목을 제거합니다. 확인창에는 저장된 이름·수량이 표시되며, 돌아가기를 누르면 미저장 수정값이 유지됩니다. 수량만 틀렸다면 기존 수정·저장을 사용하세요.

삭제는 **소비·폐기 기록을 새로 만들지 않으며 기존 이력과 통계는 유지**합니다. 소유자와 가족 모두 사용할 수 있고 공유 재고에서도 제거됩니다. 삭제 후 복구/휴지통 기능은 없습니다. 다른 가족 화면은 새로고침하거나 다시 진입하면 반영됩니다.

`DELETE /api/v1/storage-boxes/{storage_box_id}/ingredients/{ingredient_id}`는 회원 권한과 보관함 범위를 검사하고 삭제 커밋 후 204를 반환합니다. 권한 있는 보관함에서 대상이 이미 없으면 204로 처리하므로 응답 유실 후 같은 ID로 다시 요청할 수 있습니다. 삭제에 실패하면 화면의 재고를 먼저 지우지 않고 확인창에서 안내합니다. 삭제된 재료를 사용하는 미확정 스마트 차감은 재고 변경으로 보류됩니다.

## 여러 식재료 일괄 삭제·폐기

보관함 화면에서 **선택 → 식재료 체크 또는 전체 선택 → 선택한 N개 삭제/폐기**를 누릅니다. 확인창에서 대상 이름·수량을 검토한 뒤 확정합니다. 현재 보관함 안에서 한 번에 최대 100개를 처리하며, 평소에는 체크박스가 보이지 않습니다. 선택 취소나 다른 보관함 이동 시 선택을 초기화합니다.

- **삭제:** 잘못 등록한 항목을 정리합니다. 새 소비·폐기 기록을 만들지 않고 기존 이력과 통계를 보존합니다.
- **폐기:** 선택한 식재료의 **남은 수량 전체**를 제거하고 각 식재료별 폐기 이력과 통계에 기록합니다. 선택 사항인 공통 메모(최대 500자)를 각 이력에 남길 수 있습니다. 일부 수량만 버리려면 기존 개별 폐기를 사용하세요.
- 소유자와 현재 가족 회원 모두 사용할 수 있습니다. 공유 재고에서도 제거되며 처리 후 복구 기능은 없습니다. 확인창에서 돌아가면 선택은 유지됩니다.

`POST /api/v1/storage-boxes/{storage_box_id}/ingredients/bulk-action`은 선택한 항목의 이름·수량·단위·기한을 최신 재고와 비교하고 한 트랜잭션으로 처리합니다. 하나라도 변경·제거됐거나 다른 보관함 항목이면 409로 전체를 보류합니다. 중간 실패는 전체 롤백하고 커밋 후 204를 반환합니다. 같은 요청을 다시 보내도 사라진 ID 때문에 409가 되어 폐기 이력이 중복 생성되지 않습니다. 개별 삭제의 204 재시도 정책과는 구분됩니다.

권한 상실·재고 변경·연결 오류 때는 확인창에서 **목록 새로고침** 후 다시 선택합니다. 응답 유실은 완료 여부가 불명확하므로 남은 재고와 마이페이지 이력을 함께 확인하세요. 화면은 성공 응답 전 재고를 먼저 지우지 않습니다.

## 보관 기한 추천

새 영수증·음성·수동 등록에서 이름과 보관함 유형에 맞는 기준이 있으면 **추정 사용 권장일**을 자동 입력합니다. 직접 수정하거나 **제품 소비기한 / 기한 미입력 / 기한 관리 안 함**으로 바꿀 수 있습니다. 제품 소비기한은 실제 포장 날짜를 직접 확인해 입력합니다. 수정한 날짜는 보관함·이름을 바꿔도 덮어쓰지 않으며 기존 재고는 자동 변경하지 않습니다.

등록 당일의 신선한 원물과 정해진 보관 온도를 가정한 참고 날짜입니다. 제품 표시·구입 및 개봉 시점·보관 상태를 우선하세요. 가공식품·개봉 상태를 모르는 우유·기준이 없는 이름에는 임의의 날짜를 넣지 않습니다. 목록과 이력에서도 추정 권장일과 제품 소비기한을 구분합니다. 추가 AI 사용량은 없습니다. 품목별 일수·출처·조건은 [보관 기한 추천 기준](docs/expiry-guidance.md)에 정리했습니다.

## 영수증 사진으로 식재료 등록

1. 로그인 후 **대시보드·냉장고·보관함** 화면에서 **영수증으로 등록**을 누릅니다.
2. 등록할 냉장고를 선택하고 **영수증 입력 시작**을 누른 뒤 JPEG/PNG 사진 한 장을 선택합니다. 냉장고가 하나면 자동 선택되고, 냉장고 화면에서 시작하면 해당 냉장고가 선택됩니다.
3. **사진 인식하기**를 누르면 Gemini가 식재료 후보를 반환합니다. 이 단계에서는 재고가 바뀌지 않습니다.
4. 이름·수량·단위를 확인하고 필요하면 수정합니다. 제외할 항목은 체크를 해제합니다. 보관함을 고르면 기준이 있는 재료는 **추정 사용 권장일**을 자동 입력합니다. 제품에 적힌 소비기한은 구분을 바꿔 직접 입력하며, 기준이 없으면 **기한 미입력**으로 남습니다.
5. 재료마다 **보관함**을 지정합니다. 체크된 항목에 보관함을 일괄 적용한 뒤 개별 변경할 수 있습니다. 보관함 화면에서 시작한 경우 해당 보관함이 기본값입니다. 미지정 항목은 저장할 수 없습니다.
6. **선택한 N개 등록**을 누르면 지정한 보관함들에 새 재료로 한꺼번에 저장합니다. 기존 재고와 자동 합산하지 않습니다.

사진은 최대 **5MB·2천만 화소**, 후보는 최대 **20개**입니다. 사진 입력은 HEIC/PDF·여러 장·보관함 자동 분류를 지원하지 않습니다. 결제·회원 정보 등 개인정보를 제외한 상품 영역만 사용하세요. 앱은 사진을 디스크·DB에 저장하지 않고 메모리에서 검사한 뒤 카메라 방향을 적용하고 EXIF 등을 제거해 Google로 전송합니다. Google Free의 데이터 처리 정책은 별도로 적용됩니다. 실제 사진을 대상으로 한 자동 개인정보 가림 기능은 없습니다.

등록 도중 한 항목이 실패하면 여러 보관함에 걸친 전체 등록을 취소합니다. 보관함이 삭제되었으면 목록을 다시 읽고, 수정한 후보를 유지한 채 보관함을 다시 선택하도록 안내합니다. 수정 가능한 입력 오류는 내용을 유지해 재시도할 수 있습니다. 네트워크 단절·서버 오류로 저장 결과가 불명확하면 중복 등록 방지를 위해 재시도 버튼을 막습니다. 이때 입력을 닫아 냉장고의 각 보관함 재고를 확인하세요. 동일 영수증 재사용 판별이나 서버 멱등성 키는 아직 없습니다. 저장 전 후보는 새로고침·화면 이동 후 복구되지 않습니다.

기존 환경에는 `backend`에서 `.venv\Scripts\python.exe -m pip install -e ".[dev]"`를 실행해 새 이미지 검사 의존성 **Pillow**를 설치하고 백엔드를 재시작합니다. 이번 작업 환경의 `.venv`에는 Pillow 12.3.0을 설치했습니다. 프런트는 개발 서버를 실행하고 새로고침합니다. 추가 DB 마이그레이션은 없으며 기존 사용량 테이블은 필요합니다.

냉장고 단위 API는 `POST /api/v1/refrigerators/{id}/ingredients/receipt-preview`(이미지 바이너리 본문, `Content-Type: image/jpeg` 또는 `image/png`)와 `POST /api/v1/refrigerators/{id}/ingredients/batch`(`{"items": [...]}`, 각 항목에 `storage_box_id` 필수)입니다. 두 API 모두 로그인과 해당 냉장고 회원 권한을 검사하며, 저장 시 모든 보관함이 해당 냉장고에 속하는지 검사합니다. 영수증 인식 공급자 오류는 원문을 숨긴 HTTP 502, 사용량 초과는 HTTP 429로 반환합니다. 기존 보관함 단위 API도 유지합니다.

완료 범위·실제 Gemini/브라우저 검증·후속 제한은 [기능 개발 기록](docs/feature-roadmap.md#영수증-사진-초기-버전-구현검증-결과)에 정리했습니다.

## 음성으로 식재료 등록

1. 로그인 후 **대시보드·냉장고·보관함 → 음성으로 등록**을 누릅니다. 냉장고를 선택하고 **음성 입력 시작 → 녹음 시작**을 눌러 마이크 사용을 허용합니다.
2. “우유 두 팩, 계란 열 개, 사과 세 개를 등록해 줘”처럼 식재료 이름·수량·단위를 말합니다.
3. **녹음 끝내기**를 누릅니다. 최대 60초에 자동 종료되며 미리듣기와 다시 녹음을 사용할 수 있습니다.
4. **음성 인식하기**를 눌러야 녹음이 Google AI로 전송됩니다. 녹음하거나 듣는 것만으로 업로드·AI 호출·재고 저장이 발생하지 않습니다.
5. 인식 후보의 이름·수량·단위를 확인하고 수정합니다. 수량·단위가 비어 있으면 입력하고, 제외할 항목은 체크를 해제합니다. 기한은 영수증 입력과 동일한 기준표로 추천하며 제품 소비기한은 직접 입력합니다.
6. 재료별 보관함을 지정하고 **선택한 N개 등록**을 누릅니다. 사진 입력과 같은 보관함 일괄 지정·분배 저장·실패 처리 규칙을 적용합니다.

첫 버전은 **앱에서 직접 녹음, 최대 60초·20개 후보**를 지원합니다. 파일 업로드와 실시간 받아쓰기는 지원하지 않습니다. HTTPS 또는 `localhost`와 녹음을 지원하는 브라우저가 필요합니다. 휴대폰에서 일반 `http://PC주소`로 접속하면 녹음이 제한될 수 있습니다. 마이크 권한을 거절했다면 브라우저의 사이트 권한에서 허용한 뒤 다시 시도하세요.

녹음 중 탭을 숨기면 녹음을 종료하고, 취소·닫기·화면 이동 시 마이크를 해제합니다. 취소한 녹음은 버립니다. 녹음과 편집 중 후보는 새로고침 후 복구되지 않습니다. 다른 사람의 대화나 개인정보를 녹음하지 마세요. 앱 서버는 녹음을 디스크·DB·로그에 보관하지 않으며, Google Free의 데이터 처리 정책은 별도로 적용됩니다.

브라우저에서 16kHz·모노·16bit PCM WAV로 변환합니다. 서버의 `POST /api/v1/refrigerators/{id}/ingredients/voice-preview`는 `Content-Type: audio/wav` 바이너리 본문을 받고, 회원 권한·2MiB 크기·60초 길이·형식·손상·완전 무음을 검사합니다. 메타데이터를 제외한 오디오를 전달하고 AI 응답을 다시 검증합니다. 인식은 사진·레시피와 기존 한도를 공유하고, 한도 초과 시 녹음을 유지하지만 자동 재호출하지 않습니다. 기존 보관함 단위 음성 API도 유지합니다. 이번 냉장고 단위 확장에는 새 의존성·환경변수·DB 마이그레이션이 필요하지 않습니다.

AI에는 비식품 제외·말로 정정한 수량 반영·불명확한 수량 및 단위 미추정을 지시합니다. 인식 정확도를 보장하지 않으므로 저장 전에 반드시 확인하세요. Chrome 가상 마이크와 합성 한국어 음성으로 실제 Gemini·DB 흐름을 검증했으며, 실제 마이크·소음 환경·모바일 Safari/Android 기기의 호환성은 별도 확인이 필요합니다. 세부 결과는 [음성 입력 구현 기록](docs/feature-roadmap.md#음성-입력-초기-버전-구현검증-결과)을 참고하세요.

## 배포 전 JWT 키 준비

- 현재 `backend/.env`는 로컬 개발 전용입니다. **배포 전에 별도의 운영용 JWT 키를 생성하고 운영 환경의 `JWT_SECRET_KEY`에 설정해야 합니다.**
- 로컬 키를 운영에 복사하지 않습니다. 운영 키는 운영 환경변수 또는 서버의 비공개 설정 파일에 보관하며 Git에 커밋하지 않습니다.
- 동일한 배포의 모든 백엔드 프로세스는 같은 운영 키를 사용해야 합니다. 키 교체 시 재로그인 영향과 프로세스 재시작을 함께 계획합니다.
- 배포를 진행하는 세션은 이 항목을 사용자에게 다시 안내하고 운영 키 준비 여부를 확인합니다.

## 가족과 냉장고 공유

냉장고 화면의 **가족 공유**에서 소유자가 **초대 링크 만들기 → 링크 복사**를 선택해 가족에게 전달합니다. 상대방은 로그인 후 냉장고를 확인하고 **초대 수락하고 참여**를 누릅니다. 링크는 24시간 유효하며 한 명이 가입하면 소진됩니다. 소유자는 사용 전 초대를 취소할 수 있습니다. 원문 링크는 만든 직후에만 표시됩니다.

가족은 공동 식재료 조회·등록·수정·소비·폐기와 기존 AI 기능을 사용할 수 있습니다. 냉장고 이름·삭제, 보관함 생성·수정·삭제·순서 변경, 초대·회원 관리는 소유자 전용입니다. 가족은 탈퇴할 수 있고 소유자는 가족을 내보낼 수 있으며 공동 재고와 처리 이력은 보존됩니다. 소유자 탈퇴·소유권 이전은 아직 지원하지 않습니다.

상대방의 변경은 **새로고침 또는 화면 재진입** 시 확인할 수 있습니다. 로컬 확인은 같은 PC의 별도 브라우저 프로필/시크릿 창에서 다른 계정으로 진행하세요. 초대 주소는 `FRONTEND_URL`을 사용하며 localhost 링크는 다른 휴대폰에서 이 PC에 연결되지 않습니다.

이 기능에는 DB 변경이 있습니다. 다른 개발 환경에서 최신 코드를 받으면 backend 가상환경으로 아래 명령을 실행한 뒤 서버를 시작합니다. 이번 작업의 로컬 DB에는 이미 적용했습니다.

```powershell
# backend 폴더
.venv\Scripts\python.exe -m alembic upgrade head
```

상세 정책과 테스트 결과는 [기능 개발 기록](docs/feature-roadmap.md#가족-공유-초기-버전-구현검증-결과)에 있습니다.

## 메뉴 추천과 우선 활용 재료

**메뉴 추천**(`/recipes`)에서 냉장고를 고릅니다. 완제품은 간편한 준비와 곁들임을, 조리가 필요한 재료는 레시피를 안내합니다. 예를 들어 냉동 피자와 주스는 피자를 데우고 주스를 따로 마시는 자연스러운 구성을 우선합니다. 음료·간식만 있으면 한 끼로 충분하다고 꾸미지 않도록 요청합니다.

- **기한이 가까운 재료부터 활용해 볼까요?**에서 한국 날짜로 오늘~3일 이내의 재료를 확인합니다. 제품 소비기한·추정 사용 권장일을 구분하며 날짜와 실제 상태는 사용자가 확인합니다.
- 활용하고 싶은 재료를 개별로 고르거나 **임박 재료를 우선 선택**합니다. 다른 재료도 펼쳐 선택할 수 있으며 최대 30개입니다. 선택하지 않아도 냉장고 전체에서 추천합니다.
- 선택 재료는 우선 활용하되 서로 어울리지 않으면 별도 메뉴·곁들임으로 나누거나 제외 이유를 안내하도록 요청합니다. 알레르기·제외 재료 설정은 우선합니다.
- 날짜가 지난 항목은 상태 확인 영역에 분리하며 우선 선택과 스마트 차감 자동 배정에서 제외합니다. 보관함에서 제품 표시·개봉 및 보관 상태를 확인하세요. 날짜만으로 섭취 가능 여부를 판정하지 않습니다.
- 냉장고를 바꾸거나 **목록 새로고침**을 누르면 재료 선택이 초기화됩니다. 가족이 재료를 삭제하는 등 선택 대상이 바뀌면 추천을 보류하고 새로고침을 안내합니다.
- AI는 **추천 버튼을 눌렀을 때만** 호출합니다. 목록 조회·선택은 AI 사용량을 소모하지 않으며 기존 사진·음성 합산 한도를 유지합니다. 이번 임박 재료 안내는 메뉴 추천 화면에서 제공하며 대시보드 카드·자동 알림은 아직 없습니다.

`GET /api/v1/recipes/ingredients`는 접근 가능한 선택 냉장고의 재료·기한 출처·한국 기준일을 반환합니다. 기존 추천 API는 선택 필드 `priority_ingredient_ids`를 추가로 받으며, 없는/범위 밖/지난 날짜의 선택은 AI 호출 전에 409로 거절합니다. 기존 클라이언트는 이 필드를 생략할 수 있습니다. 새 DB 마이그레이션은 없습니다.

## 식사 후 스마트 차감

1. **메뉴 추천**에서 냉장고를 고르고 AI 추천을 받습니다. 기본 **1인분**, 추천 전에 **1~8인분**을 선택할 수 있습니다.
2. 식사 후 **먹은 항목 확인 · 스마트 차감**을 누릅니다. 음료·완제품을 포함해 실제 사용량을 수정하고 차감하지 않을 재료의 체크를 해제합니다.
3. **확인한 재료 일괄 차감**을 누르면 재고와 소비 이력이 함께 저장됩니다. 확인 전에는 재고를 변경하지 않습니다.

날짜가 지나지 않은 같은 이름의 재고 중 기한이 가까운 것부터 제안합니다. 메뉴의 우선 활용 선택은 특정 재고 행의 차감을 강제하지 않으므로 실제 먹은 재고를 확인하세요. g↔kg·ml↔L과 동일 단위만 자동으로 연결하며, 개↔g·약간 같은 불명확한 양은 직접 확인해야 합니다. 재고를 바꾸면 수량도 다시 입력합니다. 같은 재고를 여러 행에서 선택하면 합산합니다. 미연결·부족한 행은 직접 지정하거나 체크 해제해야 확정할 수 있습니다.

가족이 먼저 사용하여 확인 이후 재고가 바뀌면 전체 차감을 보류합니다. **최신 재고 다시 불러오기** 후 다시 확정합니다. 중복 클릭·동일 제출 재시도는 한 번만 처리하며, 응답이 끊겼을 때는 **처리 결과 확인 · 같은 요청 재시도**를 사용합니다. 새로고침은 완료 결과만 보여줍니다. 다른 날 같은 메뉴를 먹을 때만 **이 메뉴로 다시 먹기**를 누릅니다.

메뉴 추천 1회에 차감 제안도 함께 받아 기존 Gemini Free·합산 한도를 유지합니다. 재고 확인·차감 확정·다시 먹기에는 추가 AI 호출이 없습니다. AI의 재료 누락·이름·수량 오류가 가능하므로 실제 사용 재료와 양을 확인해야 합니다. 사용할 식품이 전혀 없어 안내만 반환한 경우 차감 계획은 만들지 않습니다. 이전 텍스트 레시피나 외부 레시피에는 적용되지 않습니다. 소비 이력은 아래 마이페이지에서 조회할 수 있으며, 전용 차감 되돌리기·레시피 보관함은 아직 없습니다.

새 테이블이 필요하므로 다른 개발 환경에서는 `backend` 가상환경으로 `python -m alembic upgrade head`를 실행합니다. 현재 로컬 개발 DB에는 기한 출처를 추가하는 `e4a817c2b590`까지 적용했습니다. 상세 검증·제한은 [기능 개발 기록](docs/feature-roadmap.md#스마트-차감-초기-버전-구현검증-결과)을 참고하세요.

## 마이페이지 소비·폐기 대시보드

1. 로그인 후 상단 **마이페이지** 또는 `/my`로 이동합니다. 기본은 한국 시간으로 오늘을 포함한 **최근 30일 · 내 기록 전체**입니다.
2. **기간**에서 7일·30일·90일, **처리 유형**에서 전체·소비·폐기를 선택합니다. 요약 건수, 일별 그래프, 자주 폐기한 재료 상위 5개, 상세 이력 모두 같은 조건을 따릅니다. 그래프 아래 **일별 수치 보기**로 정확한 건수를 확인할 수 있습니다.
3. **조회 범위**에서 현재 참여 중인 냉장고를 선택하면 가족 전체의 과거 기록과 메모를 볼 수 있습니다. 소유자·가족의 조회 권한은 같습니다. 탈퇴/내보내기 뒤에는 해당 가족 기록을 조회할 수 없지만, 직접 처리한 기록은 **내 기록 전체**에 남습니다. 삭제된 냉장고의 본인 기록도 당시 냉장고 이름으로 표시됩니다.
4. 상세 이력은 최신순 **20건씩** 표시합니다. 실제 수량·단위·처리자·한국 시간·당시 기한과 구분, **메모 보기**를 확인하고 이전/다음 페이지로 이동합니다. 스마트 차감의 요리 이름·인분도 메모에서 확인합니다.

재료별 처리 기록 1개를 1건으로 셉니다. 한 번 요리하며 재료 3개를 차감했다면 소비 3건입니다. 식사 횟수나 폐기 무게가 아니며 서로 다른 단위의 수량·금액을 합산하지 않습니다. 새 기록은 **새로고침**으로 반영하며, 목록 조회 정보는 1시간 후 만료되어 다시 불러와야 합니다. 다른 화면에서 돌아오거나 브라우저를 새로고침하면 기본 필터로 시작합니다.

조회 전용이며 기록 수정·삭제·재고 복구·직접 날짜 지정·파일 내보내기는 제공하지 않습니다. 추가 AI 호출·패키지·환경변수·DB 마이그레이션은 없습니다. `GET /api/v1/activity`는 로그인과 현재 가족 권한을 확인합니다. 상세 검증과 한계는 [기능 개발 기록](docs/feature-roadmap.md#마이페이지-소비폐기-대시보드-구현검증-결과)에 있습니다.

## Testing

### Backend

```bash
cd backend
python -m pytest --cov=app tests/unit/
```

테스트는 실행할 때 별도의 임시 JWT 키를 생성하여 사용합니다. 로컬·운영 JWT 키나 테스트 DB 없이도 단위 테스트를 실행할 수 있습니다. 테스트 도중 앱의 기본 DB 엔진에 연결하는 호출은 차단합니다. API 테스트는 공용 `client`/`db` 픽스처를 사용하고, 별도 세션이 필요한 서비스에는 테스트 엔진으로 만든 세션 팩토리를 전달합니다.

#### PostgreSQL 통합 테스트 안전 설정

DB 테스트는 **명시적 실행 허용과 테스트 전용 DB 주소가 모두 필요**합니다. `RECIPICK_RUN_POSTGRES_TESTS=1`이 없으면 DB 테스트를 건너뜁니다. 실행을 허용했는데 주소가 누락되거나 안전 조건을 충족하지 못하면 연결 전에 실패합니다. 앱 `DATABASE_URL`로부터 테스트 주소를 자동 생성하지 않습니다.

- `TEST_DATABASE_URL`은 **실행 셸의 환경변수**로 지정합니다. `backend/.env`에 이 이름을 추가하는 것만으로는 테스트에 적용되지 않습니다.
- `APP_ENV=development`이며 `postgresql+asyncpg`와 로컬 호스트(`localhost`, `127.0.0.1`, `::1`)만 허용합니다. 원격 DB·운영 환경은 지원하지 않습니다.
- DB 이름은 소문자로 시작하고 소문자·숫자·밑줄만 사용하며, `_test`로 끝나는 63자 이하 이름이어야 합니다. 앱 DB와 같은 이름은 사용자·호스트·포트가 달라도 거부합니다. 주소의 쿼리 매개변수도 거부합니다.
- 테스트 DB는 미리 생성해야 합니다(예: `createdb recipick_test`). 해당 DB에서 스키마를 만들 수 있는 계정을 사용합니다. 테스트 코드가 DB·계정·권한을 자동 생성하지는 않습니다.
- 각 테스트는 무작위 `recipick_test_<UUID>` 스키마만 사용합니다. `public`으로 넘어가지 않는 검색 경로를 확인하고, 종료·실패 시 자신이 만든 스키마만 정리합니다. DB 전체 테이블을 삭제하는 `drop_all`은 사용하지 않습니다.

아래 예시의 계정·비밀번호는 테스트 DB에 맞게 바꿉니다. 비밀번호의 특수문자는 URL 인코딩합니다. 다음은 PowerShell 예시입니다.

```powershell
# backend 폴더에서 실행
$env:RECIPICK_RUN_POSTGRES_TESTS = '1'
$env:TEST_DATABASE_URL = 'postgresql+asyncpg://TEST_USER:TEST_PASSWORD@127.0.0.1:5432/recipick_test'
try {
    .venv\Scripts\python.exe -m pytest tests/unit/ tests/integration/ -q -p no:cacheprovider
} finally {
    Remove-Item Env:RECIPICK_RUN_POSTGRES_TESTS
    Remove-Item Env:TEST_DATABASE_URL
}
```

레시피 사용량 테스트만 실행하려면 경로를 `tests/integration/test_recipe_usage.py`로 좁힙니다. 이 테스트도 이제 앱 개발 DB가 아닌 명시한 테스트 DB를 사용합니다. 일반 종료와 테스트 예외에는 자동 정리가 실행되지만 프로세스 강제 종료나 DB 연결 단절 시 임시 스키마가 남을 수 있습니다. 이 경우 해당 실행에서 만든 스키마를 확인한 뒤 정리하며, 다른 스키마를 일괄 삭제하지 않습니다.

### Frontend

```bash
cd frontend
npm run test
npm run lint
npm run build
```

`npm run lint`는 JavaScript·TypeScript 코드와 React Hooks 사용 방식을 정적으로 검사합니다. 사용하지 않는 변수, 잘못된 Hooks 호출, 빠진 의존성 등을 찾아내며 경고가 있어도 실패합니다. 검사 규칙은 `frontend/eslint.config.js`에 있고, 빌드 산출물인 `dist/`와 테스트 커버리지 결과는 검사에서 제외합니다.
