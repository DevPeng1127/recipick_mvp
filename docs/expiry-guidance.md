# 식재료 보관 기한 추천 기준

2026-10-30 구현. 사용자는 **등록 확인 화면에 추천 날짜를 자동 입력하고 수정 가능**하게 하는 방식을 승인했다. 새 영수증·음성·수동 등록에 적용하며, 기존 재고의 날짜는 자동 변경하지 않는다. 추가 AI 호출 없이 프런트의 고정 기준표를 사용한다.

## 날짜의 의미와 사용법

| 구분 | 저장값 | 화면 의미 |
|---|---|---|
| 추정 사용 권장일 | `estimated` + 날짜 | 기준표로 제안한 재고 관리용 날짜. 제품의 소비기한이나 안전 보장이 아님 |
| 제품 소비기한 | `label` + 날짜 | 사용자가 제품에 적힌 날짜를 확인하고 직접 입력 |
| 기한 미입력 | `unknown` + null | 정보가 없어 날짜를 정하지 않음 |
| 기한 관리 안 함 | `untracked` + null | 사용자가 명시적으로 날짜 관리를 하지 않기로 선택 |
| 기존 입력 기한 | `unknown` + 기존 날짜 | 이전 데이터의 출처를 알 수 없어 날짜만 보존 |

보관함을 지정하면 식재료명과 냉장/냉동/실온 유형에 맞는 기준이 있을 때 자동 입력한다. 자동 추천 상태에서는 이름·보관함 변경에 맞춰 갱신한다. 사용자가 날짜나 구분을 수정하거나 비우면 이후 변경으로 덮어쓰지 않으며, **추천 다시 적용**을 눌러 자동 상태로 되돌릴 수 있다. 제품 소비기한을 선택하면 기존 추정 날짜를 지워 실제 표시 날짜의 입력을 받는다. 이미 저장한 재고의 수정 화면에서는 날짜를 다시 계산하지 않는다.

목록은 `권장 D-n`, `소비기한 D-n`, 출처 미확인 날짜는 `기한 D-n`으로 구분한다. 소비·폐기·스마트 차감 이력에도 당시 날짜와 출처를 함께 보존하며 마이페이지에서 확인할 수 있다. 레시피 프롬프트도 추정일을 제품 만료일이라고 표현하지 않는다.

## 전제와 한계

- 등록 화면을 시작한 **한국 날짜 + 아래 일수**를 제안한다. 자정·월말·윤년을 달력 단위로 계산한다. 입력 중 자정이 지나도 임의로 연장하지 않는다.
- 당일 구입한 신선한 원물을 기본 전제로 한다. 냉장은 4℃ 이하, 냉동은 -18℃ 이하를 유지하는 조건이다. 실온 기준은 특히 뿌리채소에 대해 약 10~16℃의 서늘하고 건조하며 통풍되는 장소를 가정한다. 더운 실내에 그대로 적용하는 기준이 아니다.
- 예외인 `개봉한 우유`·`개봉한 요거트`는 당일 개봉을 가정한다. 실제 구입·개봉 시점, 원래 신선도, 포장, 조리·해동·온도 이탈을 앱이 알 수 없으므로 다르면 사용자가 수정해야 한다. 표시 소비기한과 제품 보관 지침이 우선한다.
- 날짜는 섭취 가능 여부를 판단하거나 자동 폐기하는 기능이 아니다. 특히 냉동 기간은 품질 관리 참고값이다. 기간을 짧게 잡는 것만으로 안전을 보장하지 않는다.
- 개봉 여부나 구입일의 별도 입력은 이번 범위에 없다. 상품명에 `우유`만 있으면 개봉 상태를 추측하지 않는다. 영수증·음성 모델은 이번에도 이름·수량·단위만 인식하며 제품 표시 날짜를 읽어오는 기능은 추가하지 않았다.
- 소금 등도 종류만으로 무기한이라고 판정하지 않는다. 기준이 없으면 미입력으로 남기고 사용자가 `기한 관리 안 함`을 선택할 수 있다.

### 이름 매칭

`frontend/src/constants/expiry.ts`가 단일 기준표다. NFKC 정규화·공백 제거, 끝의 수량/단위 표기(예: `당근 500g`, `당근(500g)`)를 정리한 뒤 완전 일치시킨다. 달걀→계란, 생닭/생닭가슴살→닭고기, 쇠고기→소고기, 다진소고기/다진돼지고기→다진고기, 양송이버섯/생양송이버섯→버섯, 적양파→양파 별칭만 허용한다.

부분 문자열·브랜드 추정·AI 분류를 사용하지 않는다. `닭고기카레`, `양파소스`, `딸기우유`, `우유`, `두부`, 기준이 없는 보관 유형은 날짜를 채우지 않는다. 인식 모델이 이름을 잘못 정리하면 원물 기준이 잘못 적용될 수 있으므로 등록 확인 절차는 유지한다.

## 저장과 호환성

마이그레이션 `e4a817c2b590`은 `ingredients`와 `ingredient_logs`에 `expiry_source`를 추가한다. 이전 행은 `unknown`이며 기존 날짜·수량·이력을 바꾸지 않는다. 다른 개발 환경은 백엔드 가상환경에서 `python -m alembic upgrade head` 후 서버를 실행한다.

API는 날짜가 필요한 출처의 null 값과 `untracked`의 날짜 입력을 422로 거절한다. 구형 클라이언트의 생성 요청은 출처 미확인으로 처리하며, 수정 요청에서 날짜만 명시하면 값이 있을 때 `label`, 비우면 `unknown`으로 해석한다. 신형 일괄 처리의 스냅샷과 스마트 차감 토큰에도 출처가 들어가 변경 충돌을 감지한다. 업데이트 이전에 발급한 차감 확인 토큰은 최신 재고를 다시 확인해야 한다.

검증·브라우저 범위와 최신 진행 상태는 [코드 점검 기록](code-audit-and-repair-log.md#현재-항목--보관-기한-추천-2026-10-30)을 따른다.
